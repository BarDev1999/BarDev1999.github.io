Multi-Broker Portfolio Data Sync

In plain words

Two brokers, two formats and no single view. This app pulls everything into one place twice a day and shows how the investments are really doing compared to the market. It can only read data, it cannot buy or sell.

What it does

Collects trades from two brokers automatically and combines them into one clean record.

Why it matters

Broker statements cannot tell you whether you are actually beating the market, or where your results came from.

What it shows about me

Building reliable data pipelines, checking numbers against known answers, and making the system read only by design.

Why deposits must not count as returns

This is the core accounting problem in one picture. The balance jumps when money is added, but the investments did not earn that jump. A flow-neutral index removes the deposit so the return can be compared with a benchmark.

How it works

Choose a stage to see what it does and the reasoning behind it.

Ingest

A headless job runs every morning and evening. One broker is read through the IBKR Flex API with polling and backoff. The other has no public API, so a Playwright session reads the portal's internal JSON API.

Why it is built this wayBroker reports are generated asynchronously and only once a day, so the sync has to wait, retry and tolerate a report that is not ready yet.
IBKR Flex APIPlaywrightTask Scheduler

Normalize

Each broker format is parsed into one trade model, with currency conversion, ticker mapping and stock splits. Row ids are deterministic, so a repeated sync cannot duplicate a trade.

Why it is built this wayNo broker feed reports splits, so they come from market history and each is applied exactly once. When a ticker mapping changes, stored rows are re-keyed rather than duplicated.
PandasFX conversionIdempotent keys

Store

Personal trades and public market prices live in two separate SQL databases. Total return indexes are computed locally from prices and dividends.

Why it is built this wayThe separation keeps the market store free of anything personal. Computing the index locally also makes results independent of the date range a data provider returns.
SQLAlchemySQLite

Analyze

Pure functions over DataFrames compute time-weighted returns, a scorecard against SPY and QQQ, risk including replays of past drawdowns, and a review of each decision. A lab tests written rules with costs and taxes.

Why it is built this wayKeeping math out of the UI means every metric can be tested alone. A missing price stays unknown instead of becoming zero, which would silently distort every total.
PandasNumPyWalk-forward tests

Deliver

A Streamlit app for deep work, plus a static phone page rebuilt after each sync and delivered through one pinned Telegram message.

Why it is built this wayA script-free static page gives phone access without running an internet-facing service against financial data.
StreamlitPlotlyTelegram Bot API

Technical detail

Optional reading for engineers and hiring managers.

  • Every ticker rendered as raw HTML is escaped, because a crafted broker CSV could otherwise run script in the browser.
  • Uploads strip null bytes, reject traversal names, and verify the resolved path stays inside the upload directory.
  • Credentials live in the operating system credential store and an untracked local environment file, not in code.
  • No write path to any broker exists, which removes the most damaging failure mode entirely.

Pure core, thin UI

All math sits in plain functions and the interface only formats. The desktop app and the phone page call the same code in the same order.

Unknown is not zero

An unavailable price is None, never 0.0. Missing history returns NaN with a reason, so a data gap cannot look like a loss.

The module keeps score of itself

It logs what it computed each day and later reports whether its own flags preceded underperformance, so weak parts can be removed.

Read only by design

The system measures and explains. It never calls a broker write API and never issues a buy or sell recommendation of its own.

  • Metrics are tested on synthetic ledgers with answers known in advance, then cross-checked against figures already proven. Real-data checks are a separate mode that I run myself.
  • Past decisions are compared with random picks drawn by permutation, after a closed form statistical test proved too generous.
  • The rule lab uses walk-forward testing with costs and taxes, and a deflated Sharpe ratio that accounts for how many variants were tried.
  • A UX audit timed the first click after the price cache expired, the case warm-cache timing misses: it went from 32.6 s to 5.2 s after the fix.

Scope, stated plainly

This is personal decision support, not investment advice. All figures come from deterministic code, and no LLM calculates any metric. I built it with Claude Code as my coding agent: I defined the requirements and acceptance criteria, reviewed the results and decided what shipped.
